# Research: مدیریت و انتشار کنترل‌شدهٔ پست‌های وبلاگ

**Feature**: `001-blog-post-management` | **Date**: 2026-10-19 | **Plan**: [plan.md](./plan.md)

این سند تصمیم‌های فنی جدیدی را ثبت می‌کند که برای اجرای Specification لازم بودند و در Constitution
تعیین نشده‌اند. تصمیم‌های سراسری قبلی (C# / ASP.NET Core / .NET 10، ساختار Solution، قواعد Project
Reference، نبود AI در نسخهٔ اولیه) دوباره تصمیم‌گیری نشده‌اند.

برچسب‌ها:

- **«کاندید Technical Baseline پروژه»**: تصمیمی که اثر آن از این Feature فراتر می‌رود و باید پیش از
  پذیرش، توسط انسان بازبینی شود.
- **محدود به Feature**: تصمیمی که فقط به همین قابلیت مربوط است.

## بخش الف: تصمیم‌های سراسری (کاندید Technical Baseline پروژه)

### R-01. سبک API: ASP.NET Core Minimal APIs

**برچسب**: کاندید Technical Baseline پروژه

- **تصمیم**: نقطه‌های ورود HTTP در `Endpoints.Api` با Minimal APIs و گروه‌بندی مسیرها
  (`MapGroup`) پیاده‌سازی می‌شوند.
- **دلیل انتخاب**: تعداد Endpointها کم است، کد کوتاه‌تر و خواناتر است و با اصل V.1 (سادگی) و نقش
  `Endpoints.Api` به‌عنوان لایهٔ نازک ورود سازگار است. منطق کسب‌وکار در Application می‌ماند.
- **گزینه‌های بررسی‌شده**:
  - Controllers (MVC): ساختار آشنا، اما Boilerplate بیشتر بدون نیاز مشخص.
  - FastEndpoints یا کتابخانه‌های مشابه: وابستگی بیرونی جدید بدون نیاز واقعی (خلاف اصل V.2).

### R-02. پایگاه دادهٔ عملیاتی: SQLite

**برچسب**: کاندید Technical Baseline پروژه (Constitution صراحتاً انتخاب پایگاه داده را باز گذاشته
است)

- **تصمیم**: SQLite به‌عنوان پایگاه دادهٔ عملیاتی نسخهٔ اولیه، با یک فایل محلی که مسیر آن از
  Connection String در پیکربندی خوانده می‌شود.
- **دلیل انتخاب**: نیاز به نصب سرور ندارد، روی Windows و Linux یکسان اجرا می‌شود، برای مقیاس آموزشی
  کافی است و آزمون‌های Integration را با حالت In-Memory همان موتور ممکن می‌کند. تعویض آن بعداً به
  دلیل استفاده از EF Core (R-03) هزینهٔ کمی دارد.
- **گزینه‌های بررسی‌شده**:
  - SQL Server / LocalDB: فقط روی Windows ساده است و نصب جداگانه می‌خواهد.
  - PostgreSQL: مناسب تولید، اما نیازمند سرور یا Docker برای هر توسعه‌دهنده.
  - ذخیره در حافظه (بدون پایگاه داده): داده با توقف برنامه از بین می‌رود و سابقهٔ وضعیت (FR-011)
    عملاً حفظ نمی‌شود.

### R-03. فناوری دسترسی به داده: Entity Framework Core

**برچسب**: کاندید Technical Baseline پروژه

- **تصمیم**: EF Core با Provider مربوط به SQLite، فقط در پروژهٔ `Infra.DataAccess`.
  `Core.Application` فقط قرارداد Repository را تعریف می‌کند و به EF Core وابسته نیست.
- **دلیل انتخاب**: ORM استاندارد .NET است، از Concurrency Token (R-11) پشتیبانی می‌کند و قاعدهٔ
  ۲ Project Reference را حفظ می‌کند.
- **گزینه‌های بررسی‌شده**:
  - Dapper: SQL دستی و مدیریت دستی Concurrency و Schema؛ پیچیدگی بیشتر برای این دامنه.
  - ADO.NET خام: کد تکراری زیاد بدون مزیت.

### R-04. مدیریت Schema: EF Core Migrations

**برچسب**: کاندید Technical Baseline پروژه

- **تصمیم**: Schema با EF Core Migrations ساخته و نگهداری می‌شود. آزمون‌ها برای پایگاه دادهٔ
  In-Memory از `EnsureCreated` استفاده می‌کنند.
- **دلیل انتخاب**: پروژه قرار است به‌تدریج رشد کند (اصل V.4)؛ Migrations تغییرات بعدی Schema را
  بدون حذف داده ممکن می‌کند. `EnsureCreated` با Migrations بعدی سازگار نیست و فقط برای آزمون مناسب
  است.
- **گزینه‌های بررسی‌شده**:
  - فقط `EnsureCreated`: ساده‌تر در شروع، اما در اولین تغییر Schema نیازمند حذف پایگاه داده است.
  - اسکریپت‌های SQL دستی: خطاپذیر و تکراری.

### R-05. چارچوب آزمون: xUnit و WebApplicationFactory

**برچسب**: کاندید Technical Baseline پروژه

- **تصمیم**: یک پروژهٔ آزمون `tests/BlogSpecLab.Tests` با xUnit. آزمون‌های واحد برای Domain و
  Application، و آزمون‌های Integration/پذیرش با `Microsoft.AspNetCore.Mvc.Testing`
  (`WebApplicationFactory`) و SQLite In-Memory.
- **دلیل انتخاب**: اصل IV آزمون خودکار قواعد Domain و موارد کاربرد را الزامی می‌کند؛ SC-001 تا
  SC-003 و SC-006 به آزمون پذیرش روی مسیر واقعی HTTP نیاز دارند. ساختار یک پروژهٔ آزمون مطابق
  Constitution است.
- **گزینه‌های بررسی‌شده**:
  - NUnit / MSTest: معادل از نظر قابلیت؛ xUnit پیش‌فرض رایج قالب‌های .NET است.
  - چند پروژهٔ آزمون جدا (Unit/Integration): خلاف ساختار Constitution و بدون نیاز فعلی.
  - EF Core InMemory Provider: رفتار رابطه‌ای و Concurrency را دقیق شبیه‌سازی نمی‌کند.

### R-06. هویت کاربر و احراز هویت

**برچسب**: کاندید Technical Baseline پروژه

- **تصمیم**:
  1. `Core.Application` هویت کاربر را فقط از قرارداد `ICurrentUser` (شناسه، نام نمایشی، نقش‌ها)
     می‌گیرد و از سازوکار احراز هویت بی‌خبر است.
  2. `Endpoints.Api` این قرارداد را از `ClaimsPrincipal` استاندارد ASP.NET Core پر می‌کند.
  3. در نسخهٔ اولیه، یک Authentication Scheme مخصوص توسعه و آزمون استفاده می‌شود که هویت را از
     Headerهای درخواست (`X-Dev-User-Id`، `X-Dev-User-Name`، `X-Dev-User-Roles`) می‌سازد. این Scheme
     فقط در محیط‌های `Development` و `Testing` ثبت می‌شود و در سایر محیط‌ها برنامه بدون آن اجرا
     می‌شود (همهٔ عملیات نیازمند ورود، 401 می‌گیرند).
  4. انتخاب سازوکار واقعی ورود (مانند JWT یا ASP.NET Core Identity) تصمیم جداگانه‌ای است و در این
     Feature گرفته نمی‌شود.
- **دلیل انتخاب**: Specification ثبت‌نام و تعیین نقش را خارج از دامنه می‌داند و فرض می‌کند «روش
  استاندارد ورود» وجود دارد. وابستگی Application به `ICurrentUser` باعث می‌شود جایگزینی بعدی
  سازوکار ورود، قواعد مجوز (اصل III.2 و III.5) را تغییر ندهد و آزمون‌ها بتوانند نقش‌های مختلف را
  به‌سادگی شبیه‌سازی کنند.
- **گزینه‌های بررسی‌شده**:
  - ASP.NET Core Identity همراه با جدول کاربران: عملاً مدیریت کاربر را وارد دامنه می‌کند که خارج
    از Specification است.
  - JWT با Identity Provider بیرونی: نیازمند انتخاب و راه‌اندازی سرویس بیرونی؛ زودهنگام.
  - بدون احراز هویت: اعمال FR-001، FR-004 و FR-013 ناممکن می‌شود.

### R-07. قالب خطا: ProblemDetails

**برچسب**: کاندید Technical Baseline پروژه

- **تصمیم**: همهٔ پاسخ‌های خطا با قالب استاندارد ProblemDetails (RFC 9457) و یک فیلد `code` پایدار
  (مثلاً `InvalidStatusTransition`) برگردانده می‌شوند. نگاشت کدهای وضعیت: 400 اعتبارسنجی، 401 ورود
  نکرده، 403 نقش نامجاز، 404 پیدا نشد یا دسترسی پنهان، 409 تعارض وضعیت یا هم‌زمانی.
- **دلیل انتخاب**: Specification در چند مورد «پیام روشن» می‌خواهد (FR-002، FR-014، Edge Cases)؛
  ProblemDetails در ASP.NET Core پشتیبانی داخلی دارد و برای آزمون پذیرش قابل بررسی است.
- **گزینه‌های بررسی‌شده**:
  - قالب خطای اختصاصی: بدون مزیت نسبت به استاندارد.
  - فقط کد وضعیت HTTP بدون بدنه: «پیام روشن» Specification را تأمین نمی‌کند.

### R-08. شناسه‌ها و زمان

**برچسب**: کاندید Technical Baseline پروژه

- **تصمیم**: شناسهٔ موجودیت‌ها `Guid` است. همهٔ زمان‌ها به UTC (`DateTimeOffset`) ذخیره می‌شوند و
  از طریق `TimeProvider` استاندارد .NET خوانده می‌شوند.
- **دلیل انتخاب**: Guid در لایهٔ Domain بدون رفت‌وبرگشت به پایگاه داده ساخته می‌شود؛ `TimeProvider`
  ترتیب زمانی (FR-010، FR-011) را در آزمون‌ها قابل کنترل می‌کند.
- **گزینه‌های بررسی‌شده**:
  - شناسهٔ عددی Auto-Increment: وابستگی ساخت موجودیت به پایگاه داده.
  - `DateTime.UtcNow` مستقیم: آزمون ترتیب زمانی را دشوار می‌کند.

### R-09. سازمان‌دهی موارد کاربرد Application

**برچسب**: کاندید Technical Baseline پروژه

- **تصمیم**: موارد کاربرد به‌صورت کلاس‌های سرویس ساده در `Core.Application` (مثلاً
  `AuthorPostService`، `EditorPostService`، `PublicPostQueries`) پیاده‌سازی می‌شوند؛ بدون Mediator،
  CQRS Framework یا Pipeline اختصاصی.
- **دلیل انتخاب**: تعداد موارد کاربرد کم است؛ اصل V.2 از Frameworkها و Abstractionهای بدون نیاز
  واقعی جلوگیری می‌کند.
- **گزینه‌های بررسی‌شده**:
  - MediatR یا کتابخانهٔ مشابه: وابستگی و غیرمستقیم‌سازی اضافه بدون نیاز.
  - یک کلاس به ازای هر مورد کاربرد: برای این حجم، فایل‌های زیاد بدون مزیت.

## بخش ب: تصمیم‌های محدود به این Feature

### R-10. مدل وضعیت پست در Domain

**برچسب**: محدود به Feature

- **تصمیم**: موجودیت `Post` در `Core.Domain` تنها مسیر تغییر وضعیت است و همهٔ انتقال‌های مجاز
  (data-model.md، بخش ماشین وضعیت) را با متدهای صریح (`Submit`، `Withdraw`، `Approve`، `Return`،
  `Publish`، `Unpublish`، `Edit`) اعمال می‌کند. هر انتقال یک `StatusChange` به سابقهٔ همان پست
  اضافه می‌کند.
- **دلیل انتخاب**: اصل III.1 قواعد وضعیت را در Domain می‌خواهد؛ متمرکز بودن انتقال‌ها، SC-001 و
  FR-011 را تضمین و آزمون‌پذیر می‌کند.
- **گزینه‌های بررسی‌شده**:
  - بررسی وضعیت در Application یا Endpoint: پراکندگی قواعد و خطر تکرار (قاعدهٔ ۶ Project Reference).
  - کتابخانهٔ State Machine: برای پنج وضعیت غیرضروری.

### R-11. هم‌زمانی: Concurrency Token و اولویت ویرایش نویسنده

**برچسب**: محدود به Feature (الگوی Concurrency Token ممکن است بعداً سراسری شود)

- **تصمیم**:
  1. `Post` یک فیلد عددی `Version` دارد که با هر تغییر افزایش می‌یابد و در EF Core به‌عنوان
     Concurrency Token تعریف می‌شود.
  2. **اقدام‌های ویراستار** (تأیید، بازگرداندن، انتشار، خارج‌کردن از انتشار) `version` دیده‌شده را
     همراه درخواست می‌فرستند. اگر با نسخهٔ فعلی برابر نباشد یا ذخیره با تعارض هم‌زمانی روبه‌رو شود،
     درخواست با 409 و کد `ConcurrencyConflict` رد می‌شود (FR-014: فقط اولین تصمیم اعمال می‌شود).
  3. **ویرایش نویسنده** به `version` وابسته نیست. اگر ذخیره با تعارض هم‌زمانی روبه‌رو شود، Application
     پست را دوباره می‌خواند و قاعدهٔ Domain را روی وضعیت تازه اجرا می‌کند (حداکثر یک تلاش مجدد).
     بنابراین اگر انتشار ویراستار زودتر ثبت شده باشد، ویرایش نویسنده همچنان اعمال و پست به «پیش‌نویس»
     برگردانده می‌شود (FR-012).
- **دلیل انتخاب**: دو قاعدهٔ متفاوت Specification (اولین تصمیم ویراستار برنده است؛ ویرایش نویسنده
  همیشه برنده است) را بدون قفل پایگاه داده و با رفتار قابل آزمون پیاده می‌کند.
- **گزینه‌های بررسی‌شده**:
  - قفل بدبینانه (Pessimistic Locking): پشتیبانی ضعیف در SQLite و پیچیدگی بیشتر.
  - آخرین نوشتن برنده (بدون کنترل): FR-014 را نقض می‌کند.

### R-12. تأیید نویسنده پیش از ویرایش پست تأییدشده یا منتشرشده

**برچسب**: محدود به Feature

- **تصمیم**: درخواست ویرایش، فیلد `confirmRevertToDraft` دارد. اگر پست در وضعیت «تأییدشده» یا
  «منتشرشده» باشد و این فیلد `true` نباشد، درخواست با 409 و کد `ConfirmationRequired` و پیامی که
  پیامد ویرایش را توضیح می‌دهد رد می‌شود و هیچ تغییری ذخیره نمی‌شود.
- **دلیل انتخاب**: FR-012 اعلام پیامد و گرفتن تأیید پیش از ذخیره را الزامی می‌کند؛ اعمال این قاعده در
  سمت سرور، آن را مستقل از رابط کاربری و قابل آزمون می‌کند.
- **گزینه‌های بررسی‌شده**:
  - فقط هشدار در رابط کاربری: در API قابل دور زدن است و قابل آزمون نیست.
  - Endpoint جداگانه برای «بازگرداندن به پیش‌نویس»: دو درخواست برای یک کار و حالت میانی ناخواسته.

### R-13. پنهان‌سازی پست‌های غیرقابل دسترس

**برچسب**: محدود به Feature

- **تصمیم**: اگر نویسنده به پست منتشرنشدهٔ نویسندهٔ دیگری دسترسی بخواهد، یا ویراستار پست «پیش‌نویس»
  یا «بازگشت برای اصلاح» دیگران را بخواهد، یا خواننده پست غیرمنتشرشده‌ای را بخواهد، پاسخ 404 است
  (نه 403). 403 فقط وقتی برگردانده می‌شود که نقش کاربر برای آن نوع عملیات کافی نیست.
- **دلیل انتخاب**: FR-004 و SC-003 جلوگیری از دسترسی را می‌خواهند؛ 404 حتی وجود پست را فاش نمی‌کند.
- **گزینه‌های بررسی‌شده**: 403 برای همهٔ موارد: وجود پست‌های دیگران را آشکار می‌کند.

### R-14. نام نویسنده و انجام‌دهنده

**برچسب**: محدود به Feature

- **تصمیم**: شناسه و نام نمایشی نویسنده هنگام ایجاد پست، و شناسه و نام انجام‌دهنده در هر
  `StatusChange`، از `ICurrentUser` گرفته و روی همان رکورد ذخیره می‌شوند. جدول کاربران ساخته
  نمی‌شود.
- **دلیل انتخاب**: مدیریت کاربران خارج از دامنه است؛ FR-010 نام نویسنده و FR-011 انجام‌دهنده را
  می‌خواهد.
- **گزینه‌های بررسی‌شده**: جدول کاربران محلی: خارج از دامنهٔ Specification و نیازمند همگام‌سازی.

### R-15. قواعد اعتبارسنجی متن

**برچسب**: محدود به Feature

- **تصمیم**: عنوان و متن پیش از اعتبارسنجی از فاصله‌های ابتدا و انتها پاک می‌شوند؛ هر دو باید
  غیرخالی باشند. طول با تعداد نویسه‌های رشته (`string.Length`) سنجیده می‌شود: عنوان حداکثر ۲۰۰ و متن
  حداکثر ۵۰٬۰۰۰. این قاعده در Domain اعمال می‌شود و هم هنگام ایجاد و ویرایش و هم هنگام ارسال بررسی
  می‌شود.
- **دلیل انتخاب**: Clarification جلسهٔ 2026-10-22 هر دو را الزامی با سقف مشخص تعریف کرده است؛
  نویسه‌های فارسی در یک واحد UTF-16 قرار می‌گیرند و `string.Length` برای آن‌ها دقیق است.
- **گزینه‌های بررسی‌شده**: شمارش Text Element (Grapheme): دقیق‌تر برای ایموجی‌ها اما پیچیده‌تر و
  بدون نیاز در Specification.

### R-16. فهرست‌ها بدون صفحه‌بندی

**برچسب**: محدود به Feature

- **تصمیم**: فهرست‌های نویسنده، ویراستار و خوانندگان در نسخهٔ اولیه صفحه‌بندی ندارند. ترتیب
  فهرست خوانندگان براساس `LastPublishedAt` نزولی است؛ فهرست‌های نویسنده و ویراستار براساس آخرین
  تغییر نزولی.
- **دلیل انتخاب**: Specification صفحه‌بندی نمی‌خواهد و مقیاس پروژه آموزشی است (اصل V.2).
- **گزینه‌های بررسی‌شده**: صفحه‌بندی از ابتدا: پیچیدگی بدون نیازمندی؛ در صورت نیاز بعداً اضافه
  می‌شود.

### R-17. نگهداری آخرین دلیل بازگشت و سابقهٔ انتشار

**برچسب**: محدود به Feature

- **تصمیم**: `Post` فیلدهای `LastReturnReason` و `LastPublishedAt` را نگه می‌دارد. `LastPublishedAt`
  با هر انتشار به‌روز می‌شود و پس از خارج‌کردن از انتشار یا بازگشت به پیش‌نویس پاک نمی‌شود؛ وجود
  مقدار آن یعنی «پست حداقل یک بار منتشر شده است» و حذف را ممنوع می‌کند (FR-003).
- **دلیل انتخاب**: نمایش فهرست نویسنده (FR-005، SC-006) و قاعدهٔ حذف بدون جست‌وجو در سابقه ساده و
  سریع می‌شود؛ سابقهٔ کامل همچنان در `StatusChange` حفظ می‌شود.
- **گزینه‌های بررسی‌شده**: محاسبه از سابقهٔ وضعیت در هر درخواست: Queryهای پیچیده‌تر بدون مزیت.
