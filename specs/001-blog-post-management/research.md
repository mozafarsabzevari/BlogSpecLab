# پژوهش و تصمیم‌های فنی: مدیریت و انتشار کنترل‌شدهٔ پست‌های وبلاگ

| مشخصه | مقدار |
|-------|-------|
| قابلیت | `001-blog-post-management` |
| تاریخ | 2026-10-19 |
| طرح | [plan.md](./plan.md) |

این سند تصمیم‌های فنی جدیدی را ثبت می‌کند که برای اجرای Specification لازم بودند و در Constitution
تعیین نشده‌اند. تصمیم‌های سراسری قبلی، یعنی C# و ASP.NET Core روی .NET 10، ساختار Solution، قواعد
وابستگی پروژه‌ها و نبود هوش مصنوعی در نسخهٔ اولیه، دوباره تصمیم‌گیری نشده‌اند.

برچسب تصمیم‌ها:

- **کاندید Technical Baseline پروژه**: اثر تصمیم از این قابلیت فراتر می‌رود و پیش از پذیرش باید
  توسط انسان بازبینی شود.
- **محدود به این قابلیت**: تصمیم فقط به همین قابلیت مربوط است.

## بخش الف: تصمیم‌های سراسری (کاندید Technical Baseline پروژه)

### R-01. سبک API

- **تصمیم:** مسیرهای HTTP در پروژهٔ `Endpoints.Api` با Minimal APIs و گروه‌بندی مسیرها
  (`MapGroup`) پیاده‌سازی می‌شوند.
- **دلیل:** تعداد مسیرها کم است و کد کوتاه‌تر و خواناتر می‌شود. این روش با اصل سادگی (V.1) و نقش
  لایهٔ API به‌عنوان لایه‌ای نازک سازگار است؛ منطق کسب‌وکار در Application می‌ماند.
- **گزینه‌های بررسی‌شده:**
  - Controllers در MVC: آشنا، اما کد تکراری بیشتر بدون نیاز مشخص.
  - کتابخانه‌هایی مانند FastEndpoints: وابستگی بیرونی جدید بدون نیاز واقعی (خلاف اصل V.2).

### R-02. پایگاه دادهٔ عملیاتی

Constitution انتخاب پایگاه داده را صراحتاً باز گذاشته است؛ بنابراین این تصمیم مهم‌ترین مورد برای
بازبینی است.

- **تصمیم:** SQLite به‌عنوان پایگاه دادهٔ نسخهٔ اولیه، با یک فایل محلی که مسیر آن از تنظیمات
  برنامه (Connection String) خوانده می‌شود.
- **دلیل:** به نصب سرور نیاز ندارد، روی Windows و Linux یکسان اجرا می‌شود، برای مقیاس آموزشی کافی
  است و آزمون‌ها می‌توانند از حالت درون‌حافظه‌ای همان موتور استفاده کنند. به‌خاطر استفاده از EF Core
  (R-03)، تعویض آن در آینده هزینهٔ کمی دارد.
- **گزینه‌های بررسی‌شده:**
  - SQL Server یا LocalDB: فقط روی Windows ساده است و نصب جداگانه می‌خواهد.
  - PostgreSQL: مناسب محیط عملیاتی، اما برای هر توسعه‌دهنده به سرور یا Docker نیاز دارد.
  - نگهداری داده فقط در حافظه: داده با توقف برنامه از بین می‌رود و سابقهٔ وضعیت (FR-011) حفظ
    نمی‌شود.

### R-03. فناوری دسترسی به داده

- **تصمیم:** EF Core با درایور SQLite، فقط در پروژهٔ `Infra.DataAccess`. پروژهٔ `Core.Application`
  فقط قرارداد Repository را تعریف می‌کند و به EF Core وابسته نیست.
- **دلیل:** ابزار استاندارد .NET برای دسترسی به داده است، از کنترل هم‌زمانی (R-11) پشتیبانی
  می‌کند و قاعدهٔ ۲ وابستگی پروژه‌ها را حفظ می‌کند.
- **گزینه‌های بررسی‌شده:**
  - Dapper: نوشتن دستی SQL و مدیریت دستی هم‌زمانی و ساختار جدول‌ها؛ پیچیدگی بیشتر.
  - ADO.NET خام: کد تکراری زیاد بدون مزیت.

### R-04. مدیریت ساختار پایگاه داده

- **تصمیم:** ساختار جدول‌ها با EF Core Migrations ساخته و نگهداری می‌شود. آزمون‌ها برای پایگاه دادهٔ
  درون‌حافظه‌ای از `EnsureCreated` استفاده می‌کنند.
- **دلیل:** پروژه قرار است به‌تدریج رشد کند (اصل V.4) و Migrations تغییرات بعدی را بدون حذف داده
  ممکن می‌کند. `EnsureCreated` با تغییرات بعدی سازگار نیست و فقط برای آزمون مناسب است.
- **گزینه‌های بررسی‌شده:**
  - فقط `EnsureCreated`: شروع ساده‌تر، اما با اولین تغییر ساختار باید پایگاه داده حذف شود.
  - اسکریپت‌های SQL دستی: خطاپذیر و تکراری.

### R-05. چارچوب آزمون

- **تصمیم:** یک پروژهٔ آزمون `tests/BlogSpecLab.Tests` با xUnit. آزمون‌های واحد برای Domain و
  Application، و آزمون‌های پذیرش HTTP با WebApplicationFactory و SQLite درون‌حافظه‌ای.
- **دلیل:** اصل IV آزمون خودکار قواعد دامنه و موارد کاربرد را الزامی می‌کند. معیارهای SC-001 تا
  SC-003 و SC-006 به آزمون روی مسیر واقعی HTTP نیاز دارند. داشتن یک پروژهٔ آزمون مطابق ساختار
  Constitution است.
- **گزینه‌های بررسی‌شده:**
  - NUnit یا MSTest: از نظر قابلیت معادل‌اند؛ xUnit پیش‌فرض رایج قالب‌های .NET است.
  - چند پروژهٔ آزمون جداگانه: خلاف ساختار Constitution و بدون نیاز فعلی.
  - درایور InMemory در EF Core: رفتار پایگاه دادهٔ واقعی و هم‌زمانی را دقیق شبیه‌سازی نمی‌کند.

### R-06. جداسازی احراز هویت از مجوز

- **تصمیم:**
  1. احراز هویت فقط مشخص می‌کند درخواست متعلق به کدام کاربر است. پروژهٔ `Core.Application` این
     اطلاعات را فقط از قرارداد `ICurrentUser` می‌گیرد که شامل «وارد شده است یا نه» و شناسهٔ کاربر
     است. هیچ نقشی از احراز هویت به دست نمی‌آید.
  2. نقش‌های فعلی کاربر هنگام هر عملیات حساس، از منبع سمت سرور (جدول نقش‌های کاربران در پایگاه
     داده) و از طریق قرارداد `IUserAccessReader` خوانده می‌شوند. اگر نقشی در پایگاه داده حذف شود،
     از درخواست بعدی اثر دارد.
  3. هیچ ورودی Client، شامل سرآیند، بدنهٔ درخواست یا محتوای Token، نمی‌تواند نقش، مالکیت یا مجوز
     ایجاد کند. مالکیت پست همیشه با شناسهٔ نویسندهٔ ذخیره‌شده روی پست بررسی می‌شود.
  4. سازوکار مشخص ورود در این قابلیت (Token مبهم، R-18) جزو این تصمیم سراسری نیست و می‌تواند
     بعداً عوض شود، بدون اینکه قواعد مجوز در Application تغییر کنند.
- **دلیل:** اصل III.2 و III.5 بررسی مجوز را در مسیر قابل اعتماد می‌خواهند. اگر نقش از ورودی Client
  بیاید، هر کاربری می‌تواند خود را ویراستار معرفی کند. جدا بودن این دو مسئولیت، تعویض روش ورود را
  بی‌اثر بر قواعد مجوز می‌کند.
- **گزینه‌های بررسی‌شده:**
  - نقش‌ها از سرآیند درخواست (نسخهٔ قبلی همین طرح): Client خودش نقش را تعیین می‌کند؛ ناامن.
  - نقش‌ها از Claimهای داخل یک Token امضاشده مانند JWT: تا انقضای Token تغییر نقش اعمال نمی‌شود و
    Token به منبع اصلی مجوز تبدیل می‌شود.
  - ASP.NET Core Identity کامل: مدیریت کاربر را وارد دامنه می‌کند که خارج از Specification است.

### R-07. قالب پاسخ خطا

- **تصمیم:** همهٔ خطاها با قالب استاندارد ProblemDetails (RFC 9457) و یک فیلد ثابت `code` برگردانده
  می‌شوند. کدهای وضعیت HTTP:
  - 400: خطای اعتبارسنجی
  - 401: کاربر وارد نشده است
  - 403: نقش کاربر کافی نیست
  - 404: پست پیدا نشد یا برای کاربر قابل مشاهده نیست
  - 409: وضعیت پست با عملیات سازگار نیست
  - 412: نسخهٔ ارسال‌شده در `If-Match` قدیمی است (R-11)
  - 428: سرآیند `If-Match` الزامی است و ارسال نشده (R-11)
- **دلیل:** Specification در چند مورد «پیام روشن» می‌خواهد (FR-002، FR-014 و موارد مرزی). این قالب در
  ASP.NET Core پشتیبانی داخلی دارد و در آزمون پذیرش قابل بررسی است.
- **گزینه‌های بررسی‌شده:**
  - قالب خطای اختصاصی: مزیتی نسبت به استاندارد ندارد.
  - فقط کد وضعیت HTTP بدون توضیح: «پیام روشن» موردنظر Specification را تأمین نمی‌کند.

### R-08. شناسه‌ها و زمان

- **تصمیم:** شناسهٔ موجودیت‌ها از نوع `Guid` است. همهٔ زمان‌ها به UTC و با نوع `DateTimeOffset`
  ذخیره و از طریق `TimeProvider` استاندارد .NET خوانده می‌شوند.
- **دلیل:** شناسه در لایهٔ دامنه و بدون مراجعه به پایگاه داده ساخته می‌شود. `TimeProvider` ترتیب
  زمانی (FR-010 و FR-011) را در آزمون‌ها قابل کنترل می‌کند.
- **گزینه‌های بررسی‌شده:**
  - شناسهٔ عددی خودافزا: ساخت موجودیت به پایگاه داده وابسته می‌شود.
  - استفادهٔ مستقیم از ساعت سیستم: آزمون ترتیب زمانی دشوار می‌شود.

### R-09. سازمان‌دهی موارد کاربرد

- **تصمیم:** موارد کاربرد در پروژهٔ `Core.Application` به‌صورت چند کلاس سرویس ساده پیاده‌سازی
  می‌شوند: `AuthorPostService`، `EditorPostService` و `PublicPostQueries`. از Mediator، چارچوب CQRS
  یا زنجیرهٔ پردازش اختصاصی استفاده نمی‌شود.
- **دلیل:** تعداد موارد کاربرد کم است و اصل V.2 از چارچوب‌ها و انتزاع‌های بدون نیاز واقعی جلوگیری
  می‌کند.
- **گزینه‌های بررسی‌شده:**
  - MediatR یا کتابخانهٔ مشابه: وابستگی و پیچیدگی اضافه بدون نیاز.
  - یک کلاس برای هر مورد کاربرد: برای این حجم، فایل‌های زیاد بدون مزیت.

## بخش ب: تصمیم‌های محدود به این قابلیت

### R-10. مدل وضعیت پست

- **تصمیم:** موجودیت `Post` در `Core.Domain` تنها مسیر تغییر وضعیت است. همهٔ انتقال‌های مجاز
  ([data-model.md](./data-model.md)) با متدهای صریح انجام می‌شوند: `Submit`، `Withdraw`، `Approve`،
  `Return`، `Publish`، `Unpublish` و `Edit`. هر انتقال یک رکورد به سابقهٔ وضعیت همان پست اضافه
  می‌کند.
- **دلیل:** اصل III.1 قواعد وضعیت را در دامنه می‌خواهد. متمرکز بودن انتقال‌ها، SC-001 و FR-011 را
  تضمین و آزمون‌پذیر می‌کند.
- **گزینه‌های بررسی‌شده:**
  - بررسی وضعیت در Application یا لایهٔ API: قواعد پراکنده و تکراری می‌شوند (قاعدهٔ ۶ وابستگی‌ها).
  - کتابخانهٔ State Machine: برای پنج وضعیت غیرضروری است.

### R-11. هم‌زمانی با Version، ETag و If-Match

طبق Technical Baseline، این روش برای کل پروژه اجباری نیست و محدود به این قابلیت است.

- **تصمیم:**
  1. هر پست یک `Version` از نوع `Guid` دارد که با هر تغییر محتوا یا وضعیت، مقدار تازه‌ای می‌گیرد.
     EF Core از آن برای تشخیص تغییر هم‌زمان استفاده می‌کند.
  2. پاسخ‌های مسیرهای نویسنده و ویراستار برای یک پست، نسخهٔ فعلی را در سرآیند `ETag` برمی‌گردانند.
     پاسخ‌های عمومی هیچ نسخه‌ای را نشان نمی‌دهند.
  3. همهٔ فرمان‌های تغییر وضعیت، یعنی ارسال، پس گرفتن و حذف توسط نویسنده و تأیید، بازگرداندن، انتشار
     و خارج‌کردن از انتشار توسط ویراستار، سرآیند `If-Match` با نسخهٔ دیده‌شده را الزامی دارند:
     - اگر `If-Match` ارسال نشود: 428 با کد `PreconditionRequired`.
     - اگر قالب آن نامعتبر باشد: 400 با کد `InvalidIfMatch`.
     - اگر نسخه قدیمی باشد، یا ذخیره با تغییر هم‌زمان روبه‌رو شود: 412 با کد `StaleVersion`.
     - اگر نسخه درست باشد ولی وضعیت پست اجازهٔ عملیات را ندهد: 409 با کد `InvalidStatusTransition`.

     بنابراین از دو تصمیم هم‌زمان ویراستارها، فقط اولی اعمال می‌شود (FR-014).
  4. پاسخ‌های 409 و 412 فقط پس از بررسی دسترسی کاربر، وضعیت و نسخهٔ فعلی (`currentStatus` و
     `currentVersion`) را برمی‌گردانند و هرگز محتوای پست را شامل نمی‌شوند.
  5. **استثنای ویرایش نویسنده (FR-012):** ویرایش (`PUT`) به `If-Match` وابسته نیست. اگر ذخیره با
     تغییر هم‌زمان روبه‌رو شود، Application پست را دوباره می‌خواند و قاعدهٔ دامنه را روی وضعیت تازه
     اجرا می‌کند (حداکثر یک تلاش دوباره). پس حتی اگر انتشار ویراستار زودتر ثبت شده باشد، ویرایش
     نویسنده اعمال و پست به «پیش‌نویس» برگردانده می‌شود، همان‌طور که شفاف‌سازی Specification
     می‌خواهد.
- **دلیل:** الگوی استاندارد HTTP برای جلوگیری از اجرای فرمان روی وضعیت قدیمی است و تفکیک «نسخهٔ
  قدیمی» (412) از «وضعیت ناسازگار» (409) را روشن می‌کند. `Version` از نوع `Guid` قابل حدس یا
  شمارش نیست. استثنای ویرایش نویسنده برای حفظ قاعدهٔ تأییدشدهٔ Specification لازم است.
- **گزینه‌های بررسی‌شده:**
  - شمارندهٔ عددی نسخه در بدنهٔ درخواست (نسخهٔ قبلی همین طرح): غیراستاندارد و بدون تفکیک 412 از 409.
  - الزام `If-Match` برای ویرایش نویسنده هم: ویرایش نویسنده پس از انتشار هم‌زمان رد می‌شد و با
    FR-012 در تعارض بود.
  - قفل کردن رکورد در پایگاه داده: پشتیبانی ضعیف در SQLite و پیچیدگی بیشتر.
  - پذیرفتن آخرین ذخیره بدون کنترل: FR-014 را نقض می‌کند.

### R-12. تأیید نویسنده پیش از ویرایش پست تأییدشده یا منتشرشده

- **تصمیم:** درخواست ویرایش، فیلدی به نام `confirmRevertToDraft` دارد. اگر پست «تأییدشده» یا
  «منتشرشده» باشد و این فیلد `true` نباشد، درخواست با 409 و کد `ConfirmationRequired` رد می‌شود،
  پیامد ویرایش در پیام خطا توضیح داده می‌شود و هیچ تغییری ذخیره نمی‌شود.
- **دلیل:** FR-012 اعلام پیامد و گرفتن تأیید پیش از ذخیره را الزامی می‌کند. اعمال این قاعده در
  سمت سرور، آن را مستقل از رابط کاربری و قابل آزمون می‌کند.
- **گزینه‌های بررسی‌شده:**
  - فقط هشدار در رابط کاربری: از طریق API قابل دور زدن و غیرقابل آزمون است.
  - مسیر جداگانه برای «بازگرداندن به پیش‌نویس»: دو درخواست برای یک کار و حالت میانی ناخواسته.

### R-13. پنهان‌سازی پست‌های غیرقابل دسترس

- **تصمیم:** در موارد زیر پاسخ 404 است، نه 403:
  - نویسنده پست منتشرنشدهٔ نویسندهٔ دیگری را بخواهد.
  - ویراستار پست «پیش‌نویس» یا «بازگشت برای اصلاح» دیگران را بخواهد.
  - خواننده پست منتشرنشده‌ای را بخواهد.

  پاسخ 403 فقط وقتی برگردانده می‌شود که نقش کاربر برای آن نوع عملیات کافی نباشد.
- **دلیل:** FR-004 و SC-003 جلوگیری از دسترسی را می‌خواهند و پاسخ 404 حتی وجود پست را فاش نمی‌کند.
- **گزینهٔ بررسی‌شده:** پاسخ 403 برای همهٔ موارد، که وجود پست‌های دیگران را آشکار می‌کند.

### R-14. اطلاعات کاربران و نام‌ها

- **تصمیم:** یک جدول حداقلی کاربران (`Users`) و یک جدول نقش‌ها (`UserRoles`) فقط برای خواندن هویت و
  نقش ساخته می‌شوند. ثبت‌نام، ویرایش مشخصات یا مدیریت نقش از طریق API وجود ندارد و این داده‌ها فقط با
  دستور راه‌اندازی محلی (R-20) ایجاد می‌شوند. نام نویسنده هنگام ایجاد پست، و نام انجام‌دهنده در هر
  تغییر وضعیت، از جدول کاربران خوانده و روی همان رکورد ذخیره می‌شود.
- **دلیل:** R-06 برای نقش‌ها منبع سمت سرور می‌خواهد و Specification وجود کاربران و نقش‌ها را از پیش
  فرض می‌کند. ذخیرهٔ نام روی رکورد، سابقه را حتی پس از تغییر نام کاربر دقیق نگه می‌دارد (FR-010 و
  FR-011).
- **گزینه‌های بررسی‌شده:**
  - بدون جدول کاربران (نسخهٔ قبلی همین طرح): منبع سمت سرور برای نقش‌ها وجود نداشت.
  - خواندن نام از جدول کاربران در هر نمایش: پرس‌وجوی اضافه و تغییر سابقه با تغییر نام.

### R-15. قواعد اعتبارسنجی عنوان و متن

- **تصمیم:** فاصله‌های ابتدا و انتهای عنوان و متن پیش از بررسی حذف می‌شوند و هر دو باید غیرخالی
  باشند. طول با تعداد نویسه‌های رشته (`string.Length`) سنجیده می‌شود: عنوان حداکثر ۲۰۰ و متن حداکثر
  ۵۰٬۰۰۰ نویسه. این قاعده در دامنه اعمال می‌شود و هنگام ایجاد، ویرایش و ارسال بررسی می‌شود.
- **دلیل:** شفاف‌سازی جلسهٔ 2026-10-22 هر دو را الزامی و با سقف مشخص تعریف کرده است. هر نویسهٔ
  فارسی یک واحد رشته است و این روش برای آن دقیق است.
- **گزینهٔ بررسی‌شده:** شمارش نویسه‌های قابل مشاهده (برای ایموجی‌ها دقیق‌تر)، که پیچیده‌تر است و
  Specification به آن نیاز ندارد.

### R-16. فهرست‌ها بدون صفحه‌بندی

- **تصمیم:** فهرست‌های نویسنده، ویراستار و خوانندگان در نسخهٔ اولیه صفحه‌بندی ندارند. فهرست
  خوانندگان براساس زمان آخرین انتشار و فهرست‌های نویسنده و ویراستار براساس زمان آخرین تغییر،
  از جدید به قدیم مرتب می‌شوند.
- **دلیل:** Specification صفحه‌بندی نمی‌خواهد و مقیاس پروژه آموزشی است (اصل V.2).
- **گزینهٔ بررسی‌شده:** صفحه‌بندی از ابتدا، که پیچیدگی بدون نیازمندی است و در صورت نیاز بعداً
  اضافه می‌شود.

### R-17. نگهداری آخرین دلیل بازگشت و سابقهٔ انتشار

- **تصمیم:** هر پست دو فیلد `LastReturnReason` (آخرین دلیل بازگشت) و `LastPublishedAt` (زمان آخرین
  انتشار) دارد. زمان آخرین انتشار با هر انتشار به‌روز می‌شود و پس از خارج‌کردن از انتشار یا بازگشت به
  پیش‌نویس پاک نمی‌شود. وجود مقدار در این فیلد یعنی پست حداقل یک بار منتشر شده و حذف آن ممنوع است
  (FR-003).
- **دلیل:** نمایش فهرست نویسنده (FR-005 و SC-006) و قاعدهٔ حذف، بدون جست‌وجو در سابقه ساده و سریع
  می‌شوند؛ سابقهٔ کامل همچنان حفظ می‌شود.
- **گزینهٔ بررسی‌شده:** محاسبه از روی سابقهٔ وضعیت در هر درخواست، که پرس‌وجوها را پیچیده‌تر می‌کند.

### R-18. ورود با Token مبهم (Opaque Bearer Token)

طبق Technical Baseline، این روش ورود دائمی پروژه نیست و محدود به این قابلیت است.

- **تصمیم:**
  - Client در سرآیند `Authorization` مقدار `Bearer <token>` را می‌فرستد.
  - Token یک رشتهٔ تصادفی ۳۲ بایتی با کدگذاری base64url است و هیچ اطلاعاتی در خود ندارد.
  - سرور در هر درخواست Token را در پایگاه داده جست‌وجو می‌کند. اگر Token پیدا نشود، منقضی شده باشد
    یا کاربرش غیرفعال باشد، پاسخ 401 است.
  - تاریخ انقضا اختیاری است. Token با حذف از پایگاه داده فوراً باطل می‌شود.
  - احراز هویت با یک AuthenticationHandler سفارشی در `Endpoints.Api` انجام می‌شود که فقط شناسهٔ کاربر
    را تولید می‌کند (R-06).
- **دلیل:** چون سرور هر Token را بررسی می‌کند، ابطال فوری است و هیچ ادعایی از Client پذیرفته
  نمی‌شود. با امکانات استاندارد ASP.NET Core و بدون بستهٔ اضافه پیاده‌سازی می‌شود.
- **گزینه‌های بررسی‌شده:**
  - JWT: نیازمند مدیریت کلید امضا؛ ابطال پیش از انقضا دشوار است.
  - Cookie: مناسب مرورگر است، نه یک HTTP API.
  - انقضای کوتاه اجباری: در محیط آموزشی نیاز به صدور مکرر Token ایجاد می‌کند.

### R-19. نگهداری امن Token

- **تصمیم:** فقط Hash نوع SHA-256 هر Token در جدول `AccessTokens` با Index یکتا ذخیره می‌شود. مقدار
  خام Token فقط یک بار هنگام صدور نمایش داده می‌شود و هرگز ذخیره یا در Log ثبت نمی‌شود. محاسبهٔ Hash و
  جست‌وجو در پیاده‌سازی قرارداد `IAccessTokenReader` در `Infra.DataAccess` انجام می‌شود.
- **دلیل:** اصل III.6؛ دسترسی به پایگاه داده، Token قابل استفاده در اختیار کسی قرار نمی‌دهد. چون Token
  تصادفی و طولانی است، یک Hash سریع کافی است.
- **گزینه‌های بررسی‌شده:**
  - ذخیرهٔ خام Token: نشت پایگاه داده برابر با نشت دسترسی همهٔ کاربران است.
  - الگوریتم‌های کند مخصوص گذرواژه (مانند PBKDF2): برای Token تصادفی غیرضروری‌اند و هر درخواست را
    کند می‌کنند.

### R-20. راه‌اندازی محلی کاربران و Tokenها

- **تصمیم:** کاربران، نقش‌ها و Tokenها با حالت خط فرمان همان برنامهٔ `Endpoints.Api` ساخته می‌شوند:
  - `provision-user`: یک کاربر با نام و نقش‌های مشخص و یک Token برای او می‌سازد و Token را یک بار
    چاپ می‌کند.
  - `issue-token`: برای کاربر موجود یک Token جدید صادر می‌کند.
  - هر دو دستور می‌توانند مدت اعتبار اختیاری بگیرند.

  این حالت فقط در محیط Development اجرا می‌شود، به پایگاه دادهٔ ساخته‌شده با Migrations نیاز دارد و
  خودش Migration انجام نمی‌دهد. اجرای عادی HTTP هیچ داده یا Migration ضمنی ایجاد نمی‌کند. منطق ساخت
  داده در `Infra.DataAccess` است و Api فقط آرگومان‌ها را می‌خواند. آزمون‌ها کاربران و Tokenها را
  مستقیماً در پایگاه دادهٔ آزمون می‌سازند.
- **دلیل:** Specification ثبت‌نام را خارج از دامنه می‌داند و وجود کاربران و نقش‌ها را فرض می‌کند.
  ساخت داده فقط با اقدام صریح انجام می‌شود و پروژهٔ جدیدی لازم نیست (اصل II.8).
- **گزینه‌های بررسی‌شده:**
  - مسیر ورود با نام کاربری و گذرواژه: رفتار جدیدی است که Specification تعریف نکرده است.
  - ساخت خودکار کاربران هنگام اجرای برنامه: دادهٔ ضمنی و احتمال Token ثابت در کد (خلاف اصل III.6).
  - پروژهٔ Console جداگانه: پروژهٔ اضافه بدون نیاز.
