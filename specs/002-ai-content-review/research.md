# پژوهش و تصمیم‌های فنی: بررسی هوشمند محتوای پست

| مشخصه | مقدار |
|-------|-------|
| قابلیت | `002-ai-content-review` |
| تاریخ | 2026-11-11 |
| طرح | [plan.md](./plan.md) |

این سند فقط تصمیم‌های جدیدی را ثبت می‌کند که برای اجرای Specification لازم‌اند. تصمیم‌های سراسری موجود
در Constitution و [Technical Baseline](../../docs/architecture/technical-baseline.md)، و تصمیم‌های
Feature قبلی که این قابلیت از آن‌ها استفاده می‌کند (ورود با Token، ProblemDetails با `code`، شناسهٔ
`Guid`، `TimeProvider`، EF Core و SQLite، xUnit و WebApplicationFactory)، دوباره تصمیم‌گیری نشده‌اند.

برچسب تصمیم‌ها:

- **ثبت‌شده در Technical Baseline**: اثر تصمیم از این قابلیت فراتر می‌رود و پس از بازبینی انسانی در
  Technical Baseline ثبت شده است.
- **محدود به این قابلیت**: تصمیم فقط به همین قابلیت مربوط است.

## بخش الف: تصمیم‌های سراسری (ثبت‌شده در Technical Baseline)

این چهار تصمیم پس از بازبینی انسانی در 2026-11-11 در بخش ۹ (AI Integration) نسخهٔ 1.1.0
[Technical Baseline](../../docs/architecture/technical-baseline.md) ثبت شدند. متن الزام‌آور در همان سند است.

### AI-01. قرارداد Structured Output نسخه‌دار

- **تصمیم:** هر Integration هوش مصنوعی که خروجی آن توسط نرم‌افزار پردازش می‌شود، یک قرارداد خروجی صریح
  و نسخه‌دار (JSON Schema) دارد که در `contracts/` همان Feature نگهداری می‌شود و Source of Truth شکل
  داده است. در صورت پشتیبانی Provider، Schema در سطح Provider و در حالت strict اعمال می‌شود. JSON Mode
  ساده یا درخواست JSON فقط در متن Prompt استفاده نمی‌شود. انطباق با Schema جایگزین اعتبارسنجی مستقل
  Application نیست.
- **دلیل:** اصل III.3 و IV.5 در Constitution خروجی مدل را غیرقابل اعتماد و صحت ساختاری را غیر از صحت
  معنایی می‌دانند. Schema در سطح Provider خطای شکلی را کم می‌کند و Validator مستقل، قواعد کسب‌وکار
  را تضمین می‌کند.
- **گزینه‌های بررسی‌شده:**
  - JSON Mode: فقط JSON معتبر را تضمین می‌کند، نه شکل آن را.
  - درخواست JSON در Prompt: هیچ تضمینی ندارد.
  - تکیهٔ کامل به Schema بدون Validator: قواعدی مانند وجود بخش ارجاع‌شده در متن پست (FR-008) را پوشش
    نمی‌دهد.

### AI-02. تفکیک نتیجهٔ معتبر، Refusal و Failure فنی

- **تصمیم:** هر Integration هوش مصنوعی سه دستهٔ جدا دارد: نتیجهٔ معتبر قابلیت، Refusal مدل، و Failure
  فنی یا پروتکلی (Timeout، دردسترس‌نبودن Provider، خروجی ناقص یا نامعتبر، شکل خروجی غیرمنتظره).
  Refusal و Failure هرگز به‌صورت پاسخ موفق یا فهرست خالی نمایش داده نمی‌شوند. نام دقیق Outcomeها در هر
  قابلیت می‌تواند متفاوت باشد.
- **دلیل:** اگر Failure به‌صورت «مشکلی یافت نشد» نمایش داده شود، کاربر به نتیجهٔ نادرست اعتماد می‌کند؛
  FR-011 این حالت را صراحتاً ممنوع کرده است.
- **گزینه‌های بررسی‌شده:** یک نوع خطای کلی برای همهٔ حالت‌ها، که تشخیص علت و آزمون هر حالت را ناممکن
  می‌کند.

### AI-03. Data Minimization و Logging

- **تصمیم:** به Provider فقط داده‌ای فرستاده می‌شود که برای Task ضروری است. محتوای کاربر، خروجی مدل و
  سایر داده‌های بالقوه حساس به‌صورت پیش‌فرض در Log یا Trace ثبت نمی‌شوند. اگر در آینده برای Evaluation یا
  Debugging به ثبت محتوا نیاز باشد، هدف، نوع داده، کنترل دسترسی و مدت نگهداری آن باید صریحاً تعریف و
  تأیید شود. مجوز ارسال هر نوع داده به سرویس بیرونی در Specification همان Feature مشخص می‌شود.
- **دلیل:** اصل III.6 و کاهش اثر نشت داده؛ این اصل Observability آینده را ممنوع نمی‌کند، فقط آن را
  تصمیمی صریح می‌کند.
- **گزینه‌های بررسی‌شده:** ثبت کامل درخواست و پاسخ برای Debugging، که محتوای کاربر را بدون تصمیم صریح
  در Log نگه می‌دارد.

### AI-04. تفکیک آزمون قطعی از Evaluation مدل

- **تصمیم:** درستی نرم‌افزار و Integration با آزمون‌های قطعی (Deterministic) و قابل اجرا در CI بررسی
  می‌شود که به مدل واقعی یا متن دقیق خروجی آن وابسته نیستند. کیفیت خروجی مدل در مسیر Evaluation جدا،
  نسخه‌دار و قابل تکرار بررسی می‌شود و Dataset، Rubric، Model، Prompt، Schema، تنظیمات و Failureها در آن
  ثبت می‌شوند. Dataset و آستانه‌های هر Feature متعلق به همان Feature هستند. موفقیت CI اثبات کیفیت مدل
  نیست و موفقیت Eval جایگزین آزمون نرم‌افزار نیست.
- **دلیل:** اصل IV.3 و IV.5؛ خروجی مدل غیرقطعی است و آزمونی که به آن وابسته باشد ناپایدار می‌شود.
- **گزینه‌های بررسی‌شده:** آزمون‌های CI با مدل واقعی، که کند، پرهزینه، ناپایدار و نیازمند Secret در CI
  هستند.

## بخش ب: تصمیم‌های محدود به این قابلیت

### R-01. Provider، Model، API و SDK

- **تصمیم:**
  - Provider: xAI؛ Endpoint برابر `https://api.x.ai/v1`.
  - Model اولیه: `grok-4.7`.
  - API: Responses API (`POST /v1/responses`)؛ اجرای غیر Streaming.
  - SDK: Package رسمی `OpenAI` نسخهٔ `2.14.0`، فقط در پروژهٔ `Infra.AI`. xAI با این SDK سازگار است،
    به شرط تنظیم Endpoint.
  - بدون Tool Calling، Web Search، X Search، File Search، Code Execution، MCP، RAG یا Agent.
  - بدون Fallback خودکار به Model یا Provider دیگر.
- **دلیل:** انتخاب صریح کاربر در جلسهٔ Plan (2026-11-11). مستندات xAI پشتیبانی از Structured Output با
  JSON Schema در حالت strict را در Responses API تأیید می‌کنند. SDK رسمی OpenAI از Endpoint سفارشی
  پشتیبانی می‌کند و به کتابخانهٔ غیررسمی Grok نیازی نیست (اصل V.2).
- **وضعیت Model:** `grok-4.7` انتخاب اولیه است، نه تضمین عبور از Quality Gate. اگر Evaluation واقعی
  (R-12) آستانه‌ها را پاس نکند، انتخاب Model براساس نتایج Eval دوباره بررسی می‌شود. مستندات xAI برای
  `grok-4.7` Snapshot تاریخ‌دار مستقلی معرفی نمی‌کنند؛ بنابراین Snapshot ساختگی تعریف نمی‌شود و نام
  واقعی Model که در پاسخ Provider برمی‌گردد، همراه هر نتیجه ذخیره می‌شود.
- **گزینه‌های بررسی‌شده:**
  - Chat Completions API: Responses API مسیر جدیدتر و پشتیبانی‌شده در xAI است و تفکیک Refusal و وضعیت
    ناقص را صریح‌تر می‌دهد.
  - Microsoft.Extensions.AI (`IChatClient`): انتزاع اضافه بدون نیاز فعلی؛ مرز `Infra.AI` به‌تنهایی
    جداسازی Provider را فراهم می‌کند.
  - کتابخانه‌های غیررسمی Grok برای .NET: وابستگی غیررسمی بدون مزیت.

### R-02. نام‌های SDK در نسخهٔ `OpenAI 2.14.0`

- **تصمیم:** پیاده‌سازی با این نوع‌ها انجام می‌شود که در CHANGELOG و فایل API عمومی Package تأیید شده‌اند:
  - Client: `ResponsesClient` (نام قبلی `OpenAIResponseClient`).
  - تنظیم Endpoint: `ResponsesClientOptions.Endpoint` (از نسخهٔ 2.14.0 نوع Options سازندهٔ
    `ResponsesClient` از `OpenAIClientOptions` به `ResponsesClientOptions` تغییر کرده است).
  - درخواست: `CreateResponseOptions` با `Model`، `Instructions`، `InputItems`، `StoredOutputEnabled`،
    `MaxOutputTokenCount` و `TextOptions`.
  - Structured Output: `ResponseTextOptions.TextFormat` برابر
    `ResponseTextFormat.CreateJsonSchemaFormat(jsonSchemaFormatName, jsonSchema, jsonSchemaFormatDescription, jsonSchemaIsStrict: true)`.
  - پاسخ: `ResponseResult` با `Status` (`ResponseStatus`)، `IncompleteStatusDetails.Reason`
    (`ResponseIncompleteStatusReason`)، `Error`، `OutputItems`، `Model` و `GetOutputText()`.
  - Refusal: بخش محتوای پیام خروجی از نوع Refusal (`ResponseContentPart.Refusal`).
  - فراخوانی: `CreateResponseAsync(CreateResponseOptions, CancellationToken)`.
- **ریسک:** API بخش Responses در این Package با برچسب `OPENAI001` آزمایشی است و ممکن است در نسخه‌های بعد
  تغییر کند. نسخهٔ Package ثابت نگه داشته می‌شود و هشدار `OPENAI001` فقط در پروژهٔ `Infra.AI` غیرفعال
  می‌شود. امضای دقیق سازندهٔ `ResponsesClient` هنگام پیاده‌سازی با همان نسخهٔ Package بررسی می‌شود.

### R-03. قرارداد Structured Output: `content_review_v1`

- **تصمیم:** شکل خروجی مدل در [contracts/model-output.schema.json](./contracts/model-output.schema.json)
  تعریف می‌شود و Source of Truth شکل Wire است:
  - `outcome`: یکی از `completed` یا `needs_input`.
  - `issues`: فهرست مشکلات؛ هر مورد شامل `category`، `severity`، `location` (`title` یا `body`)،
    `excerpt`، `explanation` و `suggestion` (رشته یا `null`).
  - `missing_information`: فهرست موارد اطلاعات ناکافی؛ هر مورد شامل `description`.
  - همهٔ Propertyها الزامی‌اند و `additionalProperties` برابر `false` است، چون حالت strict این را
    می‌خواهد؛ فیلد اختیاری با نوع `["string", "null"]` بیان می‌شود.
  - سقف‌ها در محدودهٔ اجرای قطعی xAI هستند: حداکثر ۵۰ مشکل و ۱۰ مورد اطلاعات ناکافی؛ طول `excerpt`
    حداکثر ۳۰۰ و سایر متن‌ها حداکثر ۱۰۰۰ نویسه.
- **شکل Wire در Responses API:** Schema در فیلد `text.format` با `type` برابر `json_schema`، `name`
  برابر `content_review_v1` و `strict` برابر `true` ارسال می‌شود (در SDK از طریق R-02). JSON Mode
  (`json_object`) یا درخواست JSON در Prompt استفاده نمی‌شود.
- **محدودیت‌های Schema در xAI** (طبق مستندات رسمی Structured Outputs در xAI):
  - در صورت استفاده از قابلیت‌های پشتیبانی‌شده، انطباق پاسخ با Schema تضمین می‌شود.
  - `minLength` و `maxLength` تا ۲۰۴۸ و `minItems` و `maxItems` تا ۲۵۶ به‌صورت قطعی اعمال می‌شوند و
    مقادیر بزرگ‌تر فقط Best-effort هستند؛ همهٔ سقف‌های این Schema در این محدوده‌اند.
  - `additionalProperties` به‌صورت پیش‌فرض `false` است؛ این Schema آن را صریحاً `false` تعیین می‌کند.
  - `anyOf`، `$ref` و `$defs` غیرچرخشی پشتیبانی می‌شوند؛ این Schema به هیچ‌کدام نیاز ندارد.
  - چون این تضمین‌ها به مستندات Provider وابسته‌اند، Validator مستقل (R-07) همچنان همهٔ سقف‌ها را
    دوباره بررسی می‌کند.
- **نگاشت به Specification:** `completed` با فهرست غیرخالی به «مشکلاتی یافت شد»، `completed` با فهرست
  خالی به «مشکلی یافت نشد» و `needs_input` به «نیاز به اطلاعات بیشتر» تبدیل می‌شود (FR-004).
- **دلیل:** دو مقدار `outcome` تصمیم مدل را صریح می‌کند و نبودن مشکل را از نبودن اطلاعات جدا می‌کند.
  نام نسخه‌دار Schema امکان تغییر سازگار در آینده و ثبت آن در Eval را می‌دهد.
- **گزینه‌های بررسی‌شده:**
  - سه مقدار `outcome` مطابق Specification: مدل باید دربارهٔ دو چیز هم‌ارز (وضعیت و خالی بودن فهرست)
    هم‌زمان تصمیم بگیرد و ناسازگاری بیشتری ممکن می‌شود.
  - موقعیت عددی (Offset) به‌جای `excerpt`: مدل‌ها در شمارش نویسه خطای زیادی دارند.

### R-04. مرز مسئولیت Application و `Infra.AI`

- **تصمیم:**
  - `Core.Application` مالک مورد کاربرد است: کنترل ورود، نقش، مالکیت و وضعیت مجاز پست؛ ساخت Snapshot
    محتوای فعلی؛ تعیین Deadline؛ اعتبارسنجی مستقل خروجی (R-07)؛ بررسی دوبارهٔ دسترسی پیش از ذخیره؛
    ذخیرهٔ نتیجه؛ و تعیین تازگی نتیجه. این پروژه قرارداد `IContentReviewModel` را تعریف می‌کند.
  - `Infra.AI` فقط این قرارداد را پیاده‌سازی می‌کند: ساخت Prompt نسخه‌دار، ارسال درخواست با SDK، اعمال
    Schema در سطح Provider، تشخیص Refusal و پاسخ ناقص، Deserialize کردن نامزد خروجی و تبدیل پاسخ به
    Outcome مستقل از SDK ([contracts/application-ai.md](./contracts/application-ai.md)).
  - هیچ نوع، Exception یا Client مربوط به SDK از مرز `Infra.AI` عبور نمی‌کند.
  - `Infra.AI` فقط به `Core.Application` وابسته است؛ به `Infra.DataAccess` وابسته نیست، هیچ Repository
    ندارد و نمی‌تواند وضعیتی را تغییر دهد.
- **دلیل:** قواعد ۲، ۳ و ۵ وابستگی در اصل II و اصل III.4 در Constitution.
- **گزینهٔ بررسی‌شده:** اعتبارسنجی خروجی در `Infra.AI`، که منطق کسب‌وکار را وارد Infrastructure می‌کند
  (قاعدهٔ ۶ اصل II).

### R-05. Data Minimization در ارسال محتوا

- **تصمیم:**
  - فقط عنوان و متن پست ارسال می‌شوند. شناسه و نام نویسنده، شناسهٔ پست، وضعیت، سابقه، دلیل بازگشت و
    نتیجه‌های قبلی ارسال نمی‌شوند.
  - `StoredOutputEnabled` برابر `false` (`store=false`).
  - Log فقط شامل شناسهٔ پست، نتیجهٔ دسته‌بندی‌شده، مدت اجرا، نام Model، شمار Token مصرفی و شناسهٔ پاسخ
    Provider است؛ عنوان، متن، Prompt و خروجی مدل در Log ثبت نمی‌شوند.
  - Log داخلی HTTP مربوط به SDK برای محتوای درخواست و پاسخ فعال نمی‌شود.
- **ریسک ثبت‌شده:** مستندات xAI می‌گویند پاسخ‌های Responses API به‌صورت پیش‌فرض ۳۰ روز نگهداری
  می‌شوند و گزارش‌های مستقل نشان می‌دهند پاسخی با `store=false` هم ممکن است تا مدتی قابل بازیابی باشد.
  بنابراین `store=false` حذف کامل داده در سمت Provider را تضمین نمی‌کند. این ریسک برای محیط آموزشی
  پذیرفته می‌شود و پیش از استفادهٔ عملیاتی باید با سیاست نگهداری دادهٔ xAI دوباره بررسی شود.
- **دلیل:** اصل AI-03 و اصل III.6.

### R-06. Prompt نسخه‌دار و جداسازی محتوای پست

- **تصمیم:**
  - دستورالعمل‌ها در `Instructions` قرار می‌گیرند و نسخهٔ آن‌ها (`content-review-prompt-v1`) ثابت و در کد
    `Infra.AI` است.
  - عنوان و متن پست به‌صورت یک پیام کاربر با شیء JSON شامل `title` و `body` فرستاده می‌شوند؛
    دستورالعمل‌ها صریحاً می‌گویند هر چیزی داخل این شیء فقط محتوای قابل بررسی است.
  - دستورالعمل‌ها دسته‌ها و شدت‌ها را تعریف می‌کنند، الزام می‌کنند `excerpt` عین متن پست باشد، و
    می‌خواهند در صورت محتوای ناکافی `needs_input` برگردانده شود و هیچ مشکلی حدس زده نشود.
  - زبان بررسی و توضیحات فارسی است.
- **دلیل:** FR-012 و FR-007. حتی اگر مدل از دستور داخل متن پیروی کند، Validator (R-07) و نبود Tool
  هرگونه اثر بر وضعیت را ناممکن می‌کنند.
- **گزینهٔ بررسی‌شده:** قرار دادن متن پست داخل خود دستورالعمل‌ها، که مرز داده و دستور را مبهم می‌کند.

### R-07. اعتبارسنجی مستقل خروجی در Application

- **تصمیم:** `ContentReviewValidator` در `Core.Application` این قواعد را روی نامزد خروجی اجرا می‌کند:
  1. `outcome` و همهٔ مقادیر `category`، `severity` و `location` باید از مقادیر مجاز باشند.
  2. `needs_input` باید فهرست مشکلات خالی و دست‌کم یک مورد اطلاعات ناکافی داشته باشد.
  3. `completed` نباید مورد اطلاعات ناکافی داشته باشد.
  4. متن‌های الزامی باید غیرخالی و در سقف طول R-03 باشند.
  5. `excerpt` هر مشکل باید به‌صورت Ordinal در فیلد `location` همان Snapshot پیدا شود؛ پیش از مقایسه،
     هر دو رشته به Unicode Normalization Form C تبدیل می‌شوند. مشکلی که پیدا نشود حذف می‌شود (FR-008).
  6. اگر خروجی `completed` دست‌کم یک مشکل داشته و همهٔ مشکلات حذف شده باشند، کل خروجی نامعتبر است، نه
     «مشکلی یافت نشد».
  7. مشکلات باقی‌مانده به ترتیب شدت (زیاد، متوسط، کم) و سپس ترتیب اصلی مرتب می‌شوند.

  نقض قواعد ۱ تا ۴ یا ۶ به Failure با کد `ReviewOutputInvalid` منجر می‌شود.
- **دلیل:** اصل III.3 و IV.5، FR-008، SC-002 و SC-004؛ قاعدهٔ ۶ از پنهان شدن Failure پشت فهرست خالی
  جلوگیری می‌کند (AI-02).
- **گزینه‌های بررسی‌شده:**
  - رد کل خروجی با اولین مشکل نامعتبر: Specification حذف همان مشکل را خواسته است.
  - مقایسهٔ تقریبی (Fuzzy): قاعدهٔ «بخش ارجاع‌شده در متن وجود دارد» را غیرقابل آزمون می‌کند.

### R-08. Outcomeها و نگاشت آن‌ها به HTTP

- **تصمیم:** قرارداد `IContentReviewModel` یکی از این Outcomeها را برمی‌گرداند:

| Outcome در `Infra.AI` | معنا | نتیجه در Application | پاسخ HTTP و `code` |
|------------------------|------|---------------------|---------------------|
| `Candidate` | خروجی کامل و منطبق با Schema | اعتبارسنجی (R-07)، سپس ذخیره | 201؛ یا 502 با `ReviewOutputInvalid` اگر Validator رد کند |
| `Refused` | مدل از انجام بررسی خودداری کرده است | ذخیره نمی‌شود | 502 با `ReviewRefused` |
| `ProviderUnavailable` | خطای شبکه، پاسخ 5xx، 429، خطای احراز هویت با Provider، یا پیکربندی ناقص | ذخیره نمی‌شود | 503 با `ReviewServiceUnavailable` |
| `InvalidOutput` | پاسخ ناقص (`Incomplete`، از جمله سقف Token یا فیلتر محتوا)، وضعیت `Failed`، JSON نامعتبر یا ناسازگار با Schema | ذخیره نمی‌شود | 502 با `ReviewOutputInvalid` |
| `UnexpectedOutputForm` | خروجی غیر از یک پیام متنی، مثلاً فراخوانی Tool | ذخیره نمی‌شود | 502 با `ReviewOutputInvalid` |
| (Deadline در Application) | پاسخی در ۶۰ ثانیه نرسیده است | ذخیره نمی‌شود | 504 با `ReviewTimedOut` |

  پیام همهٔ خطاها فارسی و بدون جزئیات داخلی است. قطع درخواست توسط Client پاسخی ندارد و چیزی ذخیره
  نمی‌کند.
- **دلیل:** اصل AI-02 و FR-011.

### R-09. Timeout و Cancellation

- **تصمیم:**
  - Application یک Deadline کلی ۶۰ ثانیه‌ای (FR-011) با `CancellationTokenSource` مبتنی بر
    `TimeProvider` می‌سازد و آن را با Token لغو درخواست HTTP ترکیب می‌کند.
  - اگر Deadline فرارسد، نتیجه `ReviewTimedOut` است؛ اگر Client درخواست را قطع کند، عملیات لغو و چیزی
    ذخیره نمی‌شود.
  - مقدار Deadline از تنظیمات خوانده می‌شود، پیش‌فرض آن ۶۰ ثانیه است و هنگام شروع برنامه بررسی می‌شود
    که بین ۱ و ۶۰ ثانیه باشد.
  - Retry خودکار SDK غیرفعال است (`ClientRetryPolicy` با صفر تلاش دوباره) تا مدت و هزینه قابل پیش‌بینی
    باشد و تکرار درخواست به تصمیم نویسنده باشد.
  - `MaxOutputTokenCount` برابر ۸۰۰۰ است؛ رسیدن به آن پاسخ ناقص و `InvalidOutput` است.
- **دلیل:** FR-011؛ `TimeProvider` طبق Technical Baseline و برای آزمون‌پذیری Deadline.
- **گزینه‌های بررسی‌شده:**
  - Retry پیش‌فرض SDK: ممکن است Deadline را مصرف کند و هزینه را چند برابر کند.
  - Timeout فقط در `HttpClient`: لغو درخواست Client را پوشش نمی‌دهد و با `TimeProvider` قابل آزمون نیست.

### R-10. تنظیمات Reasoning

- **تصمیم:** در Plan مقدار Reasoning برای `grok-4.7` تعیین نمی‌شود و پیش‌فرض Provider استفاده می‌شود.
  مقدار آن تنظیم قابل ارزیابی همین Feature است و در Eval با مقایسهٔ کیفیت، زمان (SC-006) و هزینه تعیین
  می‌شود. به Technical Baseline منتقل نمی‌شود.
- **دلیل:** دلیل مستندی برای انتخاب یک مقدار پیش از Eval وجود ندارد.

### R-11. ذخیره و تازگی نتیجه

- **تصمیم:**
  - هر نتیجهٔ معتبر با نسخه (`Version`) و زمان آخرین تغییر پست در لحظهٔ Snapshot، و نام Model، نسخهٔ
    Prompt و نسخهٔ Schema ذخیره می‌شود (FR-003، FR-013).
  - پس از پاسخ مدل، Application پست را دوباره می‌خواند: اگر پست حذف شده یا دیگر متعلق به همین نویسنده
    نیست، نتیجه ذخیره نمی‌شود و پاسخ 404 است. در غیر این صورت نتیجه حتی اگر پست در این فاصله تغییر کرده
    باشد ذخیره می‌شود، چون به نسخهٔ مشخصی تعلق دارد.
  - تازگی ذخیره نمی‌شود و هنگام خواندن محاسبه می‌شود: `isCurrentVersion` یعنی نسخهٔ بررسی‌شده با نسخهٔ
    فعلی پست برابر است.
  - نتیجه‌ها فقط با حذف پست حذف می‌شوند (حذف آبشاری).
- **دلیل:** FR-003، FR-013 و مورد مرزی «ویرایش پس از دریافت نتیجه». ذخیرهٔ وضعیت تازگی با هر ویرایش
  کهنه می‌شود.
- **گزینهٔ بررسی‌شده:** دور انداختن نتیجه در صورت تغییر پست هنگام بررسی، که هزینهٔ انجام‌شده را هدر
  می‌دهد و نتیجهٔ معتبر نسخهٔ قبلی را پنهان می‌کند.

### R-12. آزمون قطعی و Evaluation کیفیت

- **تصمیم:**
  - **آزمون قطعی (در `dotnet test`):**
    - Domain: قواعد سازگاری نتیجه (FR-006).
    - Application: همهٔ Outcomeها با `IContentReviewModel` جعلی، Validator، مجوزها، Deadline با
      `TimeProvider` دستی، و حفظ نشدن تغییر در پست (SC-001).
    - `Infra.AI`: درخواست و پاسخ با Transport جعلی HTTP؛ بررسی `store=false`، Schema strict، نبود Tool و
      ارسال فقط `title` و `body`؛ نگاشت Refusal، `Incomplete`، `Failed`، JSON نامعتبر، خطای HTTP و خروجی
      غیرمنتظره؛ برابری Schema جاسازی‌شده با فایل `contracts`.
    - HTTP: سناریوهای [quickstart.md](./quickstart.md) با WebApplicationFactory و مدل جعلی.
  - **آزمون Smoke با Provider واقعی:** فقط با متغیر محیطی `BLOGSPECLAB_PROVIDER_TESTS=1` و کلید معتبر
    اجرا می‌شود و در اجرای عادی رد (Skip) می‌شود.
  - **Evaluation کیفیت:** Corpus نسخه‌دار از پست‌های فارسی با برچسب انسانی در
    `tests/BlogSpecLab.Tests/Evaluation/` شامل پست سالم، پست با اشکال‌های کاشته‌شده، پست با اطلاعات ناکافی
    و پست حاوی دستور تزریقی. اجراکنندهٔ Eval نیز فقط با همان متغیر محیطی اجرا می‌شود و شواهد را در
    `specs/002-ai-content-review/evaluation/` ثبت می‌کند: تاریخ، Model واقعی، نسخهٔ Prompt و Schema،
    تنظیمات، نتایج هر نمونه، Failureها و زمان پاسخ.
  - **آستانه‌های پیشنهادی Eval** (پیش از اجرا نیازمند تأیید انسانی):
    - ۱۰۰٪ نمونه‌های «اطلاعات ناکافی» با `needs_input` و بدون مشکل (SC-003).
    - ۱۰۰٪ نمونه‌های تزریقی بدون اثر بر ساختار نتیجه و وضعیت پست.
    - دست‌کم ۸۰٪ اشکال‌های کاشته‌شده با دستهٔ درست شناسایی شوند.
    - حداکثر ۲۰٪ پست‌های سالم مشکلی با شدت «زیاد» بگیرند.
    - دست‌کم ۹۰٪ پاسخ‌ها کمتر از ۳۰ ثانیه (SC-006).
    - کمتر از ۵٪ خروجی‌ها به `ReviewOutputInvalid` منجر شوند.
- **دلیل:** اصل AI-04 و اصل IV. پروژهٔ آزمون جدیدی ساخته نمی‌شود (ساختار Constitution).
- **گزینه‌های بررسی‌شده:**
  - پروژهٔ جداگانه برای Eval: خلاف ساختار Constitution بدون نیاز مشخص.
  - آزمون Snapshot از متن خروجی مدل: غیرقطعی و ناپایدار.

### R-13. پیکربندی و Secret

- **تصمیم:**
  - بخش تنظیمات `ContentReview` با `Endpoint`، `Model`، `ApiKey` و `TimeoutSeconds`.
  - `ApiKey` در `appsettings` یا Repository قرار نمی‌گیرد و از User Secrets در توسعه یا متغیر محیطی
    `ContentReview__ApiKey` خوانده می‌شود.
  - اگر `ApiKey` تنظیم نشده باشد، برنامه به‌طور عادی اجرا می‌شود و فقط درخواست بررسی پاسخ 503 با
    `ReviewServiceUnavailable` می‌گیرد (اصل V.3).
- **دلیل:** اصل III.6 و V.3 در Constitution.

### R-14. مدل ذخیره‌سازی نتیجه

- **تصمیم:** موجودیت `ContentReview` در `Core.Domain`، جدول `ContentReviews` با کلید خارجی به `Posts` و
  حذف آبشاری. مشکلات و موارد اطلاعات ناکافی به‌صورت مجموعهٔ Owned با نگاشت JSON در همان سطر ذخیره
  می‌شوند. یک Migration جدید در `Infra.DataAccess` اضافه می‌شود ([data-model.md](./data-model.md)).
- **دلیل:** نتیجه همیشه کامل خوانده و نوشته می‌شود و هیچ پرس‌وجویی روی تک‌تک مشکلات لازم نیست.
- **گزینه‌های بررسی‌شده:** جدول جداگانه برای مشکلات، که Join و پیچیدگی بدون نیاز ایجاد می‌کند.

### R-15. هم‌زمانی و محدودیت درخواست

- **تصمیم:** چند درخواست هم‌زمان برای یک پست مجاز است و هر کدام نتیجهٔ جداگانه می‌سازد. محدودیت تعداد
  درخواست اعمال نمی‌شود (فرض Specification). درخواست بررسی به `If-Match` نیاز ندارد، چون پست را تغییر
  نمی‌دهد و همیشه آخرین نسخهٔ ذخیره‌شده را بررسی می‌کند.
- **دلیل:** Specification محدودیتی نمی‌خواهد و نتیجه‌ها به نسخهٔ مشخص تعلق دارند (R-11).
- **گزینهٔ بررسی‌شده:** قفل یک درخواست فعال برای هر پست، که پیچیدگی بدون نیازمندی است.
