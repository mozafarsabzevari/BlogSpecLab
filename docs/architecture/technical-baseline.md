# Technical Baseline پروژهٔ BlogSpecLab

| مشخصه | مقدار |
|-------|-------|
| نسخه | 1.0.0 |

## ۱. هدف و دامنه

این سند فقط انتخاب‌های فنی‌ای را ثبت می‌کند که برای کل BlogSpecLab معتبرند و از این مرحله به بعد
پیش‌فرض پروژه به شمار می‌آیند. هر Plan جدید باید با آن‌ها سازگار باشد و آن‌ها را دوباره
تصمیم‌گیری نکند.

- اصول پایدار پروژه فقط در Constitution آمده‌اند. این سند آن‌ها را تکرار نمی‌کند و فقط به آن‌ها ارجاع
  می‌دهد. در صورت تعارض، Constitution مقدم است.
- تصمیم‌های موقت، آزمایشی یا مخصوص یک قابلیت اینجا ثبت نمی‌شوند و در `research.md` همان قابلیت
  می‌مانند.

## ۲. Platform

زبان، Framework و نسخهٔ هدف همان است که بخش «محدودیت‌های فناوری و دامنه» در Constitution تعیین کرده
است.

## ۳. Architecture

ساختار پروژه‌ها، مسئولیت هر پروژه، جهت وابستگی‌ها و منع Business Logic در Endpoints و Infrastructure
طبق اصل II در Constitution است. این سند قاعدهٔ معماری دیگری اضافه نمی‌کند.

## ۴. Persistence

- برای Persistence رابطه‌ای از Entity Framework Core استفاده می‌شود.
- `DbContext`، پیکربندی نگاشت و سایر جزئیات EF Core فقط در Infrastructure قرار می‌گیرند و به Domain
  نشت نمی‌کنند.
- تغییرات ساختار پایگاه داده (Schema) با EF Core Migrations مدیریت می‌شوند. Migrationها فقط با دستور
  صریح اعمال می‌شوند و هنگام Startup برنامه به‌صورت ضمنی اجرا نمی‌شوند.
- Provider پایگاه داده طبق Constitution هنوز انتخاب نشده است (بخش ۹).

## ۵. Security

این قواعد، اصل III در Constitution را برای احراز هویت و مجوز مشخص‌تر می‌کنند:

- احراز هویت (Authentication) و مجوز (Authorization) دو مسئولیت مستقل هستند و شناسایی هویت کاربر
  به‌تنهایی هیچ مجوزی ایجاد نمی‌کند.
- مجوز فعلی کاربر هنگام هر عملیات حساس از یک منبع معتبر سمت سرور خوانده می‌شود.
- ادعاهای Client، محتوای Token یا ورودی HTTP به‌تنهایی منبع حقیقت (Source of Truth) برای مجوز نیستند.

## ۶. HTTP Contracts

- خطاهای HTTP با قالب استاندارد `ProblemDetails` برگردانده می‌شوند.
- هر خطایی که Client باید آن را پردازش کند، یک `code` پایدار دارد.
- جزئیات داخلی، StackTrace، Credential و هر اطلاعات حساس دیگری در پاسخ خطا افشا نمی‌شوند.

## ۷. Testing

الزامات کلی آزمون طبق اصل IV در Constitution است. ابزارهای سراسری:

- Framework اصلی آزمون xUnit است.
- آزمون‌های Integration برای ASP.NET Core با `WebApplicationFactory` نوشته می‌شوند.

## ۸. Concurrency and Transactions

- هر مورد کاربردی که اجرای آن روی وضعیت قدیمی ممکن است نتیجهٔ کسب‌وکاری نادرست ایجاد کند، کنترل
  هم‌زمانی (Concurrency Control) صریح دارد.
- سازوکار دقیق کنترل هم‌زمانی متناسب با Aggregate، Persistence Provider و قرارداد بیرونی همان قابلیت
  انتخاب می‌شود.
- تغییرات وابسته‌ای که از نظر کسب‌وکار یک عملیات واحدند، در مرز تراکنشی مناسب و به‌صورت اتمی ذخیره
  می‌شوند.

### زمان

- همهٔ زمان‌ها به وقت UTC ذخیره می‌شوند.
- زمان جاری از طریق `TimeProvider` استاندارد .NET خوانده می‌شود، نه مستقیماً از ساعت سیستم، تا
  رفتار وابسته به زمان قابل آزمون باشد.

## ۹. تصمیم‌های هنوز باز

| موضوع | وضعیت | منشأ |
|-------|-------|------|
| Database Provider نهایی | انتخاب نشده است | Constitution |
| Model Provider و Embedding Model | هنگام ورود AI و RAG تعیین می‌شوند | Constitution |
| Authentication Provider نهایی | انتخاب نشده است | این سند |
| سبک سراسری Endpointها | تثبیت نشده است | این سند |

انتخاب‌های زیر فقط مربوط به قابلیت فعلی یا محیط آموزشی هستند و تصمیم سراسری نیستند:

- SQLite به‌عنوان پایگاه دادهٔ اصلی پروژه
- Minimal API به‌عنوان تنها سبک مجاز API
- Opaque Bearer Credential به‌عنوان روش دائمی Authentication
- `Guid` Version برای همهٔ Aggregateها
- `ETag`/`If-Match` برای همهٔ APIهای آینده

## ۱۰. نحوهٔ تغییر Technical Baseline

- تغییر تصمیم‌های این سند فقط پس از ثبت پیشنهاد تغییر، بررسی اثر آن بر Specificationها، Planها، کد و
  آزمون‌ها، و تأیید مرجع مسئول مجاز است.
- هر تغییر با افزایش نسخه و ثبت تاریخ این سند همراه است.
- تثبیت یکی از «تصمیم‌های هنوز باز» نیز تغییر Baseline محسوب می‌شود و همین روند را طی می‌کند.
- اگر تغییری با Constitution تعارض داشته باشد، ابتدا Constitution باید طبق اصل VI اصلاح شود.
